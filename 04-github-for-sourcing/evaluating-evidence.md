# Evaluating Evidence of Expertise

GitHub is valuable to recruiters because it can expose evidence of work. The hard part is interpreting that evidence responsibly.

## Use an evidence ladder

### Level 1: Interest signal

Examples:

- starred repository
- forked project
- followed topic

Useful for: hypothesis generation.

Confidence: low.

### Level 2: Participation signal

Examples:

- opened an issue
- commented on technical discussion
- submitted a small pull request
- contributed documentation

Useful for: showing direct interaction with a project or ecosystem.

Confidence: medium, depending on context.

### Level 3: Contribution signal

Examples:

- repeated merged pull requests
- meaningful authored changes
- sustained contribution to the same project
- ownership of a meaningful feature or component

Useful for: stronger evidence of hands-on experience.

Confidence: medium-high to high.

### Level 4: Stewardship signal

Examples:

- project maintainer
- release management
- reviewing others' pull requests
- roadmap or architecture discussions
- triaging issues
- long-term ownership

Useful for: evidence of responsibility, influence, or leadership within that project.

Confidence: high when clearly attributable.

## Context changes everything

A five-line documentation change can be trivial in one project and highly meaningful in another.

A contributor with only a handful of commits may have authored a major architectural change.

A person with thousands of commits may have automated or highly granular commit behavior.

Numbers without context are seductive and often misleading.

## Separate facts from conclusions

Bad sourcing note:

> Expert in Go and Kubernetes.

Better sourcing note:

> Maintains a Kubernetes operator written primarily in Go and has authored multiple merged changes related to controller behavior and deployment configuration.

The second note gives another recruiter or hiring manager something they can inspect.

## Build an evidence packet

For a prospect you care about, capture:

- profile URL
- relevant repository
- exact contribution or activity
- timeframe
- why it matters to the role
- confidence level
- what still needs validation

## The rule

**GitHub should improve your hypothesis about a candidate, not replace the conversation with the candidate.**
