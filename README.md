# GitHub Literacy for Recruiters

> Stop treating GitHub like a candidate database. Learn what people are actually doing here.

Recruiters have been taught how to **search GitHub** for years.

Far fewer have been taught how to **understand GitHub**.

That's a problem.

GitHub is not a database of software engineers. It's a place where people build, document, collaborate, experiment, learn, publish, and share their work.

If you're going to use that work to identify and engage technical talent, you should understand the environment you're looking at.

**No coding experience required.**

In fact, you're going to learn GitHub by using this repository.

By the time you're finished, you'll have starred a repository, watched a repository, created an issue, made a fork, committed a change, and submitted a pull request.

More importantly, you'll understand what those actions actually mean when you encounter them on someone else's profile.

---

## The 30-second explanation

Think of GitHub as:

**Google Drive + version history + project management + collaboration + publishing + professional identity**

Google Drive says:

> Here are my files.

GitHub says:

> Here is my project. Here is how it changed. Here is who contributed. Here is what we're working on. Here is what other people built from it.

Code is what made GitHub famous. **Code is not the only thing GitHub can hold.**

### Still feels abstract? Think community library.

Imagine a shared digital library where people can browse the shelves, save the library to their favorites, subscribe to updates, request new resources, make their own copy of the entire collection, propose additions, and see exactly who changed what over time.

That is surprisingly close to how GitHub works.

Read [The Community Library: GitHub Without Code](01-start-here/the-community-library.md), then try the model yourself in our [Community Recruiting Library](07-community-library/README.md).

## Learn GitHub by actually using GitHub

This repo is intentionally interactive.

### Your first five actions

- ⭐ **Star this repository** - learn what a star actually means.
- 👀 **Watch this repository** - experience GitHub notifications.
- 💬 **Open an issue** - introduce yourself and share one GitHub concept you want demystified.
- 🍴 **Fork this repository** - create your own copy.
- ✍️ **Contribute** - improve an analogy, example, resource, or recruiter explanation and submit a pull request.

You don't have to write code to do any of those things.

## Recruiter translation table

| GitHub concept | Recruiter-friendly translation |
| --- | --- |
| Repository | Project folder, or think of it as the whole community library |
| README | Project homepage / executive summary / library front desk |
| Commit | A saved change with a note explaining what changed |
| Commit history | Project timeline and audit trail |
| Branch | A safe working copy for experimenting |
| Pull request | Proposed changes submitted for review |
| Issue | Task, idea, question, bug, discussion item, or resource request |
| Fork | Your own connected copy of someone else's project |
| Star | Bookmark + public interest signal |
| Watch | Subscribe to updates |
| Organization | Shared workspace for a company, team, or community |
| Markdown | Simple formatting for documents |
| GitHub Pages | Turn repository content into a public website |

## A note for sourcers

Technical talent does not "live on GitHub" because GitHub happens to expose profiles recruiters can search.

People are here because **work happens here**.

The goal of this project is to help recruiters move from:

> "How do I find engineers on GitHub?"

...to:

> "What am I actually looking at, what does it tell me, and what can I responsibly infer from it?"

That shift makes GitHub sourcing dramatically better.

## Core principle

**Evidence before inference.**

A repository, contribution graph, language label, fork, star count, or organization membership can be useful context. None of those signals should be treated as a shortcut for understanding someone's actual experience.

We will teach you both what GitHub signals can tell you and what they cannot.
