# Use GitHub Yourself

The fastest way to understand GitHub is to stop observing it from the outside.

This track turns you from "recruiter who searches GitHub" into "recruiter who has actually used GitHub."

No coding required.

## Exercise 1: Star this repository

A **star** is a lightweight way to bookmark or show interest in a repository.

### Do it

Click the **Star** button at the top of this repository.

### Notice

You have now created the exact type of signal recruiters often see on someone else's profile.

Ask yourself: does starring this repo prove you are an expert in GitHub sourcing?

No.

It proves you starred it.

That distinction is the point.

---

## Exercise 2: Watch this repository

Watching subscribes you to repository activity.

### Do it

Use the **Watch** control and choose the notification level that makes sense for you.

### Notice

GitHub is not just a publishing surface. It is a living project environment with ongoing activity.

---

## Exercise 3: Open an issue

Issues are used for tasks, questions, ideas, bugs, requests, and discussions.

### Do it

Open an issue titled:

`Recruiter intro: YOUR NAME`

In the body, answer:

1. What kind of recruiting or talent work do you do?
2. What GitHub concept has always confused you?
3. What do you hope to understand better after this project?

Congratulations. You just participated in a GitHub project without writing code.

---

## Exercise 4: Fork the repository

A fork creates your own connected copy of this repository.

### Do it

Click **Fork**.

Now you have a version under your own GitHub account.

### Notice

This is why recruiters need to check whether a repository is original or forked before attributing authorship.

---

## Exercise 5: Make a commit

Inside your fork, create a file called:

`recruiter-notes/YOUR-USERNAME.md`

Add three things you learned.

When GitHub asks you to save the change, you will be creating a **commit**.

Write a useful commit message, such as:

`Add Susanna's recruiter notes`

You just created Git history.

---

## Exercise 6: Submit a pull request

Now propose that your change be added back to the original project.

Create a **pull request** from your fork.

You are effectively saying:

> I made a change in my copy. Would you like to incorporate it into yours?

That workflow is fundamental to open-source collaboration.

---

## What you can now honestly say

After completing these exercises, you have:

- used a repository
- starred and watched a project
- opened an issue
- forked a repository
- edited Markdown
- created a commit
- submitted a pull request

More importantly, these terms are no longer abstract.
