# Signal vs. Noise

GitHub can contain excellent evidence of technical work. It can also tempt recruiters into over-interpreting weak signals.

This page is the antidote.

## Stronger signals

Signals become more useful when they show **specific behavior in context**.

Examples:

- substantive merged pull requests
- maintaining a project over time
- technical discussion in issues or reviews
- repeated contribution to the same ecosystem
- documentation ownership
- releases or project stewardship
- clearly authored projects with meaningful history

## Weaker signals

These can still be useful clues, but they need investigation:

- stars
- forks
- language percentages
- follower counts
- contribution-square density
- number of repositories
- organization icons

## Common recruiter mistakes

### "They have 200 repositories, so they must be prolific."

Maybe. Or many could be forks, tutorials, abandoned experiments, generated projects, or tiny utilities.

### "Their top language is JavaScript, so they're a JavaScript engineer."

GitHub language statistics describe repository content. They are not a skills assessment.

### "Their contribution graph is empty."

That tells you their visible contribution graph is empty. It does not tell you they haven't been doing technical work.

### "They're in this GitHub organization, so they work there."

Organization relationships can mean several things. Verify employment separately.

### "This repo has 10,000 stars, so this person must be exceptional."

First determine what they actually did on the project.

## The sourcing rule

Move through this sequence:

**Signal → inspect → evidence → inference → confidence**

Do not jump from signal directly to conclusion.

## A useful test

Before writing a sourcing note, ask:

> Could I explain exactly what I saw that made me believe this?

If not, keep investigating.
